An AXT library is built in layers. Each part below rests on the ones before it, and each has vector categories that test it. The eight parts take the categories every library implements first, then the transports and sync, which depend on what the library offers.

Note

A category passes only as a whole, and some categories reach into later parts. The protocol sessions include additions and removals of devices (keys.md, section 5.5), WITHDRAW messages (shares.md, section 4.1), and CHANGE, RESYNC and FORWARD messages of another app that the app rejects (sync.md, section 7.1). The encoding category decodes the bodies of every schema of the specification. Each vector lists the sections it tests in its member refs, so a library can tell which failures belong to a part it has not built yet.

1. Avro, fingerprints and the types

AXT encodes everything with Apache Avro 1.12: the binary encoding, the single-object encoding, the object container file, the Parsing Canonical Form, CRC-64-AVRO and schema resolution (envelope.md, section 1). Where envelope.md says nothing else, the Avro specification holds.

  • Fingerprints. A fingerprint is the CRC-64-AVRO of the schema's Parsing Canonical Form, written as 8 bytes in little-endian order. The canonical form drops logicalType, so a uuid string is written as "string". At least one Avro library writes it otherwise and computes another fingerprint; the vectors catch that (section 5).
  • Schema resolution. A record is read with the writer schema and resolved against the reader schema (section 6).
  • Strings, ids and times. Strings are well-formed UTF-8, ids are uuid strings compared as 128-bit values, and times are the records of time.md, not Avro's logical types for times (section 7).
  • Limits. A message is at most 16 MiB, and a decoder checks a declared length against the input that is left before it allocates for it (section 8). A receiver decodes records up to a data depth of 32 and rejects a deeper one (types.md, section 5.7).
  • The time types. axt.Date, axt.Time, axt.DateTime and axt.Duration, their validity, zone rules that differ and adding a duration (time.md).
  • Metadata. What a receiver shows of a type and checks of its values, by its description (metadata.md).

Tested by: encoding (fingerprint), types (fingerprint, decode_record), time (fingerprint, decode_record, resolve_date_time, add_duration) and bricks (describe, check_record). The example types are listed on Example types.

2. The envelope and signatures

Every message is one axt.Envelope: its format, its kind, the sender's key, the record it is about, the body and the signature (envelope.md, section 2). The body is a single-object encoding of the kind's schema; the schemas are on Schemas. A live message and a file are encoded as sections 3 and 4 say.

Every message is signed with the sending device's Ed25519 key (keys.md, sections 2.1 and 2.2). Verification is strict: the specification fixes which keys and signatures verify, so that every library gives the same answer (section 2.3). With an Ed25519 library that checks less, the library adds steps 1 to 3 of that section before it calls it.

Tested by: encoding (decode_message, decode_body, encode_message) and keys (public_key, sign, verify, check_signing_key, verify_message).

3. Records

Every record has a stable id and a version. A receiver applies record messages by the version rule, keeps tombstones of deletions, keeps what its own user changed, and reports an outcome for each record (records.md, sections 5 to 7).

Tested by: records (apply), a session of one receiver and one sender. A library that implements records offers its apps each of the policies the vectors use: changes kept per field or for the whole record, and a deletion that deletes or keeps a record with local changes (conformance.md, section 5.3).

4. The manifest and the protocol

The manifest states which types an app takes and what it does with them. A library checks its validity and limits, decides which types fit it, and chooses the purpose sentence in the user's language (manifest.md, sections 3.6, 4 and 5.2).

The protocol is the exchange itself: the first messages and the choice of the envelope format, the offer, the answers, the record messages, the acknowledgement and the errors (protocol.md). Section 14 sums up the live connection as a state machine (protocol.md, section 14). The error codes are on Error codes.

Tested by: manifest (check_manifest, fit) and protocol (choose_format, contact_key, resend_after_removal, session). A session plays one app in one live connection.

5. Trust, sealing and device sets

The rest of keys.md:

  • Trust. The short fingerprint, first contact, known senders and forgetting a sender (keys.md, section 3).
  • Encryption for the relay. HPKE with the parameters of section 4.1, the encryption key and its check, sealing, padding and opening (section 4).
  • Device sets. The devices of one owner, each with a key of its own, that count as one sender: adding and removing a device, the chain, and receiving additions and removals (section 5).

Tested by: keys (short_fingerprint, check_encryption_key, padded_length, seal, open, device_add, device_join, join_chain, device_sets). Sealing and opening are in the category every library implements, whether or not it supports the relay.

With the device sets in place, a receiver resolves the relations of the records it holds, also to records of another sender, by any key of that sender's set (records.md, section 10). Tested by: records (relations).

6. Shares

A sender sends an app of another user only the records its user shared with it (shares.md, section 2.2). It takes one back with a WITHDRAW, which the receiver applies among its other record messages (sections 3 to 6). The receiver's user can propose a change with a PROPOSAL, which the owner takes or refuses with a PROPOSAL_REPLY (sections 12 to 16).

Tested by: shares (receive, take_version, owed, pass_withdrawal, join_receivers, offer_types, acked, owner, proposer). That a sender sends nothing beyond its shares cannot be seen by a receiver, so no vector tests it (conformance.md, section 8).

8. Sync

For a library that offers its apps more than one device for an owner: the stamps, the state of a record and the merge (sync.md, sections 2 to 6), the CHANGE and RESYNC messages between the devices of a set (sections 7 to 16), and what the set does with what it got from other apps, with FORWARD and the owner's changes of received records (sections 17 to 24).

Tested by: sync (next_stamp, change, merge, deleted, begin_stamping, stale, pass_version, shown, withdrawal_stamp, siblings). A siblings session plays one device with its siblings; most of the category's vectors are such sessions.
