Conformance is counted in categories. Each category tests one part of the specification, and a library conforms when it passes every vector of every category it implements. This page says which categories those are.

The categories

The vectors are grouped into fifteen categories, one vector file each (conformance.md, section 2.1). Nine of them every library implements. The others depend on what the library offers the apps that use it (section 2.2).

CategoryImplemented byTests
encodingEvery libraryCanonical forms and fingerprints, the envelope, the bodies of the specification's schemas
typesEvery libraryThe example types, schema resolution, the data depth limit
timeEvery libraryThe time types, their validity, other zone rules, adding a duration
recordsEvery libraryA receiver applying record messages: versions, tombstones, its user's own changes, the outcomes
manifestEvery libraryThe validity of a manifest, which types fit it, the language of the purpose sentence
keysEvery librarySigning keys, strict verification, short fingerprints, device sets, padding, sealing and opening
protocolEvery libraryOne app in a live connection
sharesEvery libraryWithdrawals at a receiver, what a sender owes, proposals at their owner and their proposer
bricksEvery libraryDescriptions of types: the schema derived from each, the descriptions that are not valid, what a receiver shows of a type, and which values break a check
fileA library that supports filesReading an AXT file
local and qrA library that supports the local networkThe frames and the HELLO; the QR payload and its text
relayA library that supports the relayThe relay as an app uses it; qr as well if the library shows or scans QR codes for it
syncA library that offers several devices for one ownerStamps, the merge, the messages between the devices of a set
relay-serverRelays, not librariesThe interface of a relay

Why these nine

Every transport carries messages, so every library encodes, signs and verifies them. Every app that receives records applies them, and the withdrawals among them. Every app that sends records to an app of another user sends only what its shares name (shares.md, section 2.2). That is why shares is asked of every library, as records is. Every offer and every file carries its types as descriptions, from which each app derives the schema (fields.md, section 9), so bricks is asked of every library as well. With it, a library offers its apps what a receiver shows of a type and the checks of its values, which a receiver need not use (metadata.md, sections 4 to 7).

The ones that depend on the library

  • Transports. AXT does not require an app to support every transport (transports.md, section 1), so it does not require it of a library. A library implements the categories of the transports it supports.
  • Sync. An installation that is a set of its own may count the versions of its records instead of stamping them (sync.md, section 2.4). A library that offers its apps more than one device for an owner, with the stamps, the merge and the messages between the devices, implements sync.

A category passes as a whole

Within a category a library implements, every vector counts. A vector that the adapter answers as unsupported fails, and with it the category. There is no partial pass of a category.

The library states which categories it implements. Its adapter names them in its first answer to the runner (Write the adapter), and the runner sends only the vectors of those categories. It names the others as not run and still exits with success when every vector it ran passed (conformance.md, section 7.1). A green run therefore proves conformance only when the adapter names at least the nine categories above.

Conforming to a version

A library conforms to one version of AXT. That it conforms to AXT 0.1.0 means that it passes at least the eight categories every library implements, with the vectors of 0.1.0 (conformance.md, section 2.2); that it conforms to AXT 0.2.0, that it passes at least the nine of 0.2.0 with its vectors. Each vector file names the version of the specification it is for in its member specification (section 3.1). The vectors of 0.1.0 and how many each category holds are listed in section 7.4.

The library states the version in its README and package metadata, and its CI proves it by running the suite of that release (Run the suite in CI).

When a vector and the text differ

The normative text of the specification governs; the vectors make it testable. They are made with the same code as the examples of the other documents, and where an example and a vector differ, the vector holds. A vector that contradicts the normative text is a fault in the vectors. It is reported as an issue and corrected in a later release of the vectors, and a library that follows the text in that point still conforms (conformance.md, section 2.3).

What the vectors leave to the library

Some rules cannot be tested with bytes and an expected result. A library covers them with tests of its own. Among them are the TLS handshake and discovery on the local network, the timers of liveness and of the protocol, what an app shows its user and asks it, the state a receiver keeps across connections apart from the keys of its known senders, and a file above 256 MiB. The full list is in conformance.md, section 8.
