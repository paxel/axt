The specification's repository holds no library. Each library has a repository, a version and a release cycle of its own, and is tied to AXT by the release whose suite it passes (ADR 2).

Before starting

Before starting a library, open an issue in paxel/axt that names the language and who maintains the library (CONTRIBUTING.md).

The repository

  • The library lives in a repository of its own, paxel/axt-<language>.
  • It has its own gates and its own tags.
  • It is published to its language's registry.
  • Its code is licensed under Apache-2.0 OR MIT (CONTRIBUTING.md).

Two versions

A library has two versions, and they are not the same:

VersionWhat it isWhere it is stated
The library's ownSemVer, set by the libraryIts tags and its registry
The AXT version it conforms toA release of AXT, such as 0.1.0, whose suite it passesIts README and package metadata, proven by the pin in its CI

The CI pins the AXT release and the SHA-256 of its archive, checks the release's attestation and runs the suite from it (Run the suite in CI). Moving the library to a new AXT version is a deliberate change of that pin.

Below 1.0, a later version of AXT may still change things in incompatible ways; each change is listed in the changelog.

The list of libraries

The README of the specification lists the libraries, with the language, the repository, the package and the AXT version each conforms to. The bar for a library is the conformance suite; it keeps passing it with every change to the library or the specification (CONTRIBUTING.md).

Changes to the suite

The suite is part of the standard. A change to it that a conforming library no longer passes is a change to the specification and needs a compatibility note. Changes are agreed in an issue before a pull request (CONTRIBUTING.md). A vector that a library finds to contradict the normative text is reported as an issue (conformance.md, section 2.3).
