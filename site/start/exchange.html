cat-a-log sends Mimi's vet appointment to Old Brain Fix over the local network. This page follows the messages of that exchange, the example of Protocol, section 17, and then says what changes through a relay and in a file.

Before the first record: the key

Apps know each other by their signing keys, not by their names. Before two apps exchange records, each user accepts the other app's key. Scanning the other app's QR code in person counts as that confirmation. In any other case, such as a file or a relay message from an unknown key, the app asks its user and shows the other app's short fingerprint to compare: trust on first use (Keys, section 3.2). Until the user accepts the key, the app applies no record signed with it.

The messages

In the example, cat-a-log's user wants to send Mimi's record and her vet appointment. Old Brain Fix's user takes the appointment but not the pet.

StepMessageWhat happens
1, 2 MANIFEST, both ways Each app sends its manifest: the types it takes, and one sentence per type on what it does with them. Neither waits for the other. Old Brain Fix says, for example, "An Appointment becomes a Reminder."
3 OFFER, cat-a-log to Old Brain Fix cat-a-log offers the types Pet and Appointment, version 1, with their full schemas. Both fit Old Brain Fix's manifest: the Appointment by its own entry, the Pet because Old Brain Fix takes any other type too.
4 ACCEPT, Old Brain Fix to cat-a-log Old Brain Fix's user takes the Appointment.
5 DECLINE, Old Brain Fix to cat-a-log The Pet, with the reason NOT_WANTED. A type that fits is not taken by itself: the receiver confirms or declines each one.
6 DATA, cat-a-log to Old Brain Fix The appointment, version 1. Its body names the schema by its fingerprint only; the full schema came with the offer.
7 ACK, Old Brain Fix to cat-a-log The outcome APPLIED: Old Brain Fix had no record under that id and took it.

The example goes on with a DATA of the pet, which cat-a-log should not have sent: its type has no accepted offer, and Old Brain Fix answers with the error NOT_ACCEPTED (Errors).

The rules behind each step:

  • The first messages of a connection: Protocol, section 3.1.
  • Which types fit a manifest, and offering only those: Manifest, section 5.
  • The offer: Protocol, section 4, schema axt.Offer.
  • Accept and decline: Protocol, section 5.
  • Applying a record and its outcome: Records, section 5 and section 7.
  • The acknowledgement: Protocol, section 7, schema axt.Ack.

Note

What a sender may offer depends on whose app the receiver is. To an app of another user, only the records that the owner shared with it leave (Shares, section 2.2). An app of the same user, such as another app on the same phone, may get records without a share, with the user's answer at each offer (Shares, section 2.3).

Later versions of the record

The appointment keeps its id for its whole life. When cat-a-log's user moves it, cat-a-log sends it again under a higher version; when the user cancels it, cat-a-log sends a DELETE. Updates and deletions go through the same steps of offer and answer as new records. A receiver whose own user changed the record keeps those changes where it can, and reports it: MERGED when it kept some fields, KEPT when it took nothing (Records, section 6). A message that arrives twice, or after a newer one, changes nothing (Records, section 5.2).

Through a relay

The messages and the rules are the same, but there is no connection. Each app sends its manifest through the relay, a sender offers by the manifest it keeps of the receiver, and answers and acknowledgements come back through the relay too. The relay may deliver late, out of order or twice; the version rule makes the result the same. Every message is sealed for the receiver's encryption key (Protocol, section 15.1).

In a file

A file has no way back to its sender. Its signed header lists the schemas in place of an offer, the user who opens the file and the reader's manifest take the place of the answer, and nothing acknowledges it. A file therefore holds no OFFER, ACCEPT, DECLINE, ACK or ERROR; the reader applies its records by the same rules and reports nothing (Protocol, section 15.2; Transports, section 2).
