An app uses AXT through a library for its language. Each library lives in a repository of its own, is versioned on its own, is published to its language's registry, and states the AXT version it conforms to.

What conforming means

A library's CI pins an AXT release and the SHA-256 of its archive, checks the release's attestation, and runs that release's conformance suite against the library's own adapter (conformance/README.md). Moving to a new AXT version is a deliberate change of that pin.

The suite is split into categories. Every library implements nine of them: encoding, types, time, records, manifest, keys, protocol, shares and bricks. The others depend on what the library offers: file, local, qr and relay for the transports it supports, metadata if it offers the field metadata, sync if it offers more than one device for an owner. A category passes only as a whole. A library that conforms to AXT 0.2.0 passes at least the nine categories every library implements, and states the others it implements (Conformance, section 2).

Why each library has its own repository

A library is only useful to an app when it is maintained, versioned, tagged and published where its language looks for packages. A directory in the specification's repository gives none of that, and several libraries in one repository would tie their release cycles together. This repository therefore holds the specification, the types, the test vectors, the conformance suite and the reference relay, and no library (ADR 2).
