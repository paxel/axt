A relay may be written in any language and store messages in any way. It is a relay of AXT when it follows transports.md, section 5, and passes the relay-server vectors. This page walks through that section; the spec is the rule.

Everything the reference relay adds, such as its file format, its sweep every 10 minutes, its default room of 64 MiB and its rate limits, is its own choice (relay.md). A relay of your own chooses its own.

Mailboxes

A mailbox holds sealed messages for one installation, its owner (transports.md, section 5.1). The owner generates a mailbox secret of 32 bytes. The mailbox id is the SHA-256 of the ASCII text AXT-v1 mailbox, one zero byte, and the 32 bytes of the secret, written as 64 lower-case hexadecimal digits.

  • Whoever knows the id can put messages into the mailbox.
  • Only the holder of the secret can create the mailbox, list, fetch and delete its messages, and delete it.
  • The relay keeps the id, not the secret. It checks a secret by computing the id from it, so a copy of its storage gives away no secret.

A relay sees neither the content of a message nor its type, and the mailbox is bound to no key.

The requests

A relay is an HTTP service, reached over HTTP/1.1 or HTTP/2 with TLS, and named by its base URL, such as https://relay.example.org/axt/. The paths are appended to the base URL (transports.md, section 5.2). {mailbox} is a mailbox id and {message} the SHA-256 of a sealed message, each as 64 lower-case hexadecimal digits. An owner request carries Authorization: Bearer, one space and the secret as 64 lower-case hexadecimal digits. The OpenAPI 3.1 document spec/relay-api.json defines every request, response, status code and header, for a relay's own tests and tools.

RequestBySuccess
PUT v1/mailboxes/{mailbox}owner201 for a new mailbox, 204 for one that exists
DELETE v1/mailboxes/{mailbox}owner204; the mailbox and its messages are gone, also for one that does not exist
PUT v1/mailboxes/{mailbox}/messages/{message}anyone201, or 204 if the relay holds the message already
GET v1/mailboxes/{mailbox}/messagesowner200 with the list of the messages held; optional query wait
GET v1/mailboxes/{mailbox}/messages/{message}owner200 with the sealed message as application/octet-stream
DELETE v1/mailboxes/{mailbox}/messages/{message}owner204, also for a message the relay does not hold

Only the list and the fetch have a body in their response. A relay requires no cookies and no header that section 5.2 does not name.

Failures

CodeWhen
400A put whose body is empty or whose SHA-256 is not {message}; a wait that is not 0 to 60; a query on another request
401An owner request without Authorization, or with one that is not a secret in the form above
403An owner request whose secret is not the mailbox's; a mailbox the relay does not create for this app
404A mailbox that does not exist, except for its deletion; a message the mailbox does not hold
411A put without Content-Length
413A put above transports.sealed_message bytes
429A request above the relay's rate limits, with Retry-After
503The relay cannot serve the request now
507A put into a mailbox that has no room

Apps act on the code: they repeat a request after 429, 503 and 507, do not repeat it after 400, 401, 403 and 413. After 404 a sender stops putting into the mailbox, and an owner whose mailbox itself is gone creates it again (sections 5.3 and 5.4).

Putting

A put is checked in this order: Content-Length is present (411) and at most transports.sealed_message (413), which the relay knows before it reads the body; the mailbox exists (404); the body is not empty and its SHA-256 is {message} (400); the relay holds the message already (204, and nothing changes); the mailbox has room (507). Then the relay holds the message (201) (transports.md, section 5.3). A put is safe to repeat: the relay holds a message once, however often it is put.

Listing, fetching and deleting

The list is a JSON object with the media type application/json. Its member messages is an array of the messages held, oldest put first, at most transports.list_messages, each an object with id, the SHA-256 as 64 lower-case hexadecimal digits, and size, its length in bytes (transports.md, section 5.4): 

{"messages":[{"id":"7cbe…","size":1073}]}

With wait from 1 to transports.list_wait and no message in the mailbox, the relay holds the response for up to that many seconds until a message is put, and then answers with the list. It may answer sooner. Without wait, or with 0, it answers at once.

Holding time

The holding time is transports.holding of types/axt/limits.json, the same for every relay, because the protocol depends on it and a sender cannot ask a relay for it (transports.md, section 5.5):

  • A relay holds each message for the holding time after its put, unless the owner deletes it first, and has deleted it once transports.longest_holding has passed since its put. A repeated put does not extend the time.
  • A relay may remove a mailbox, with its messages, when its owner has made no request for transports.mailbox_idle, and never before.

Limits it may set

From transports.md, section 5.6:

  • Size. A relay accepts sealed messages up to transports.sealed_message bytes, the largest message sealed and padded, and rejects a larger one with 413. This one is not a choice.
  • Room. A relay may limit the number and the bytes of the messages a mailbox holds, and answers a put above its limit with 507. Into an empty mailbox it accepts a message of any size it accepts at all.
  • Rates. A relay may limit the requests per client address and per mailbox, and the mailboxes created per client address, and answers a request above a limit with 429 and Retry-After.
  • Who may have a mailbox. A relay may create mailboxes only for the apps it serves, such as the users of one operator, and answer other creations with 403. How it tells them apart is not defined.

TLS and logs

Apps reach a relay only over HTTPS, with TLS 1.3 or TLS 1.2 as RFC 9325 recommends them, and check its certificate as for any HTTPS server. A relay never logs mailbox secrets or the value of Authorization, keeps no message beyond the holding time, also not in a backup, should not log mailbox ids together with client addresses, and deletes every log entry that holds both within 7 days (transports.md, section 5.7). The pages Put a proxy in front and Keep the logs within the rules show how the reference relay meets this.

Prove it

A relay passes the relay-server vectors (conformance.md, section 2.2). How to run them against your relay is on Run the relay-server vectors.
