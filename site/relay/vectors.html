Every relay passes the relay-server vectors. The conformance runner sends them to an adapter, a small program that plays each vector's requests against the relay and reports the answers. The reference relay has one; a relay of your own needs its own.

The category

relay-server tests the interface of a relay, for relays rather than libraries (conformance.md, section 2.1). A relay passes it; a library need not implement it (section 2.2). In 0.1.0 it holds 2 vectors in vectors/relay-server/relay-server.json: one session of the requests of transports.md, sections 5.2 to 5.6 and of its example of section 7.5, and one of a mailbox whose room is used up (conformance.md, section 7.4).

Against the reference relay

From the repository root:

python3 conformance/run.py --category relay-server -- python3 relay/adapter.py

The runner needs Python 3.11 or later with fastavro and cryptography. The repository's pyproject.toml and uv.lock pin them; with uv, uv sync installs them and uv run starts a script with them (conformance/README.md).

The relay and its adapter need the standard library only. The runner reports each vector that fails, and for each category how many vectors passed; it exits with 0 only when every vector it ran passed. --verbose names every vector (conformance.md, section 7.1).

What a vector asks

A relay-server vector is a session of one relay with empty storage and a clock the test sets (conformance.md, section 5.11). Its operation is relay, and its input has:

MemberContent
base_urlThe relay's base URL, such as https://relay.example.org/axt/
quota_bytesThe room of a mailbox, for the case of a full mailbox
requestsThe requests, each with method; target, the path after the base URL with its query; headers; body, as Bytes; and now, the relay's clock in seconds

The result has one entry for each request: status, and for a successful list messages, for a successful fetch message. A body is Bytes in one of two forms: a string of lower-case hexadecimal digits, or, for a large value, an object with deflate, length and sha256 (section 3.2). The second vector uses it for a message of 17,301,553 bytes, the largest a relay accepts.

The now of the requests jumps ahead by days, to test the holding time, and goes back again. The second vector has a quota_bytes of 0: the empty mailbox still takes that largest message, and the next put gets 507.

An adapter for your relay

An adapter reads one JSON request per line on its standard input and writes one JSON answer per line on its standard output, and nothing else there (conformance.md, section 6):

  1. To {"id": "hello", "op": "hello", "input": {"format": 1}} it answers with its name and the category it implements, "categories": ["relay-server"].
  2. To each vector, {"id": …, "op": "relay", "input": …}, it answers {"id": the same id, "output": {"steps": [...]}}.
  3. An operation it cannot perform it answers with "unsupported": true, and a fault of its own with "failure" and a text. Both fail the vector.
  4. It ends when the runner closes its standard input.

For each vector, the adapter needs a relay with empty storage, the vector's room, and a clock it can set to each request's now. How your relay offers this is yours to choose; the specification defines a test clock only for the reference relay. A vector expects no 429; the reference adapter turns the relay's rate limits off, so that its own requests to set the clock do not count.

Then run the suite with your adapter's command: 

python3 conformance/run.py --category relay-server -- <your adapter's command>

The vectors are made from a model of a relay that answers each request with the first check that fails, in the order of relay.md, section 3.1, the order of the reference relay. For a put, that order is the one of transports.md, section 5.3.

The reference adapter as a model

relay/adapter.py needs the standard library only. For each vector it (relay.md, section 8):

  • starts the relay as a process of its own, on 127.0.0.1 with a port the system picks, with an empty temporary storage directory, the vector's quota, no rate limits and --test;
  • sets the relay's clock with PUT /_test/now before each request;
  • sends each request with exactly the vector's headers and a Host; a request without Content-Length is sent without a body, since in HTTP/1.1 it has none;
  • returns the status, the list's messages or the fetched message as hexadecimal;
  • stops the relay and deletes its storage.

The test hook belongs to the reference relay's test mode, which never runs in production (Run the reference relay).

What the vectors leave out

For the reference relay, relay/test_axt_relay.py tests what the vectors do not: a list that waits until a put and one whose wait ends, a restart on the same storage, the sweep and the removal of an idle mailbox, the test hook without --test, the log, early answers before a body, Expect: 100-continue, several requests on one connection, the rate limits and the room. It runs with the standard library only: 

python3 -m unittest relay/test_axt_relay.py
