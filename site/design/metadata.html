A type is written as its description: typed fields put together, each with one brick. The type's Avro schema is derived from it. An app that gets a type it has never seen still has the description, and its texts and checks tell that app how to show each field, in its user's language, and which values are valid.

A type is its description

A typed field describes one field: its name, its doc, its texts, a few hints, and in its member kind one brick, such as axt.StringField or axt.EmailField. The brick says what kind of value the field holds and carries the checks and hints of that kind (fields, section 1). Every brick and its members are on Bricks.

The description of a type is a typed field whose brick is an axt.ObjectField. At this root it holds the type's full name, its version, its title field and its fields, each a typed field again, down to the values (section 9.1). Every example type is published as its description; Example types shows each one with its texts and bricks.

The kinds of bricks

  • Value bricks hold text, numbers, booleans, bytes, an enum, a list, a map, an object of further typed fields, or one of the time types (section 4).
  • Semantic bricks hold text of one form, with its check built in: CommonMark, an email address, a phone number, a web address, a URI, a colour, an IBAN, a BIC, a country, a language, a currency, a media type or a unit (section 5).
  • The relation brick holds links to other records and to things outside AXT, and the extension brick holds fields of other apps (sections 11 and 12; Link records).

The derived schema

  • A fixed rule turns a valid description into an Avro schema: each typed field becomes one field of a record, with the type, the default and the union with null that its brick and required give (section 9.2). Your library applies it; you write the description.
  • The rule gives the forms every type keeps, such as ["null", T] with the default null for a value that may be absent (types, section 5).
  • The derived schema carries none of the type's own texts, hints or checks. Its fingerprint is the type's fingerprint (fields, section 9.3).
  • An offer carries each type as its description, and a file carries the description and the derived schema of each type in its header (section 10).

Hints and checks

Each typed field holds its texts and, in its brick, its hints and checks (fields, section 1). There are two kinds:

  • A hint says how to show a type, a field or a symbol: a label, a help text, an emoji, an order. A value cannot break a hint.
  • A check is a rule a value can break: required, the format of a semantic brick such as axt.EmailField, pattern, min_length, max_length, min and max.

The description travels with the type, and none of its texts, hints or checks is in the derived schema, so none changes the type's fingerprint (fields, section 9.2). A receiver shows and checks a record by the description that came with its writer schema (metadata, section 3.4).

Labels, help and emoji

  • label is the name a receiver shows for the type, a nested type or a field, in English, such as Postal code. help is one or two sentences on what the value is or how to enter it, such as Five digits. Both are one line of plain text, within the limits metadata.label and metadata.help (section 4.1).
  • The label and the help text are written for the user. The doc is written for the developer and stays the definition of what the field means.
  • label_translations and help_translations give the same texts in other languages, keyed by language tag, such as de or pt-BR, never en. A translation needs its English text. A receiver picks the language from its user's list of languages and falls back to English (section 4.2).
  • emoji is one emoji a receiver may show next to the label, such as 📞 for a phone number. It should be one emoji that Unicode recommends for general interchange, and is never shown in place of the label (section 4.3).
  • Each symbol of an axt.EnumField has a label, help, emoji and their translations of its own (section 4.4).

Without a label, a receiver shows the field's name with underscores read as spaces (types, section 6). Every example type carries a label and an emoji on the type and on its fields (types, section 5.9).

Order and groups

  • order of a field puts it before the fields without one, the lowest first. Fields without it keep the order of the description. The order is for display only; the encoding keeps the order of the description, and its range lets a type put a new field before those it already has (section 5.1).
  • group of a field names a group, such as contact; fields with the same key are shown together. The groups of the axt.ObjectField give each group its label, emoji and translations once (section 5.2).

Inputs

For a receiver that lets its user enter or change a value (section 5.3, 5.4):

MemberWhat it says
placeholderThe text an empty input shows, such as +49301234567. It is not translated, so it should be a form any reader understands
exampleAn example value as text. In a brick of text it meets the field's checks
multilineThe value may hold several lines
preferred_lengthHow many code points an input should have room for, such as 5 for a postal code. It is not a limit
sensitiveThe value is a secret or personal data that others near the screen should not see, such as an account number
advancedMost users need not see or fill in the field

sensitive only changes how the value is shown. It does not protect the value beyond what every message has: every message is signed, and sealed through a relay (section 8).

Checks

  • A semantic brick has the form of a text built in: markdown, email, phone (E.164, such as +49301234567), url, uri, colour, iban, bic, country, language, currency, media-type or ucum. A receiver shows and offers inputs as the format suggests. Formats are checked by their syntax only, never against a registry (section 6.3).
  • pattern of an axt.StringField is a regular expression in the I-Regexp form of RFC 9485 that the whole value matches, such as [0-9]{5}. I-Regexp has no anchors and no \d (section 6.4).
  • min_length and max_length bound a text in code points, or bytes in bytes. min and max bound a number, in the field's unit (section 6.2).

Three rules decide what a check covers (section 6.1):

  • null keeps every check but required.
  • The empty string keeps every format and every pattern. A field that needs a value is required.
  • The checks of the items of a list apply to each item, not to the list.

Dates, times and ids have no formats: they are the time bricks and the logical type uuid.

What a check binds

A check binds your app as a sender; it only lets the receiver refuse (section 7.1):

  • Your app never sends a record with a value that breaks a check of the description of the type it writes the record with.
  • A receiver may check the values against your description and may reject a record that breaks one with VALUE_INVALID, naming the field, such as address.postal_code, so that your user can correct it.
  • A receiver that takes such a record anyway keeps and shows the value as it came. It never changes the value to meet the check, such as by removing the spaces of a phone number.

That is why adding or narrowing a check is not a compatible change, while widening or removing one is, and why labels and translations can change in any version (types, section 3.3; Evolve a type).

A description that breaks a rule

A description that breaks a rule of the bricks, such as a pattern that is not an I-Regexp, is not valid (fields, section 6). Your app never offers one, and a receiver declines its type with DESCRIPTION_INVALID (section 10.1). The derived schema carries no axt. attribute but axt.version and those of the published schemas of axt.Relation and axt.Extension that it holds (section 9.2).

An example

The illustration com.example.Vet of fields, section 8, is described by bricks: a phone, an email address and a website in the group contact, an IBAN that is sensitive and advanced, a number of minutes between 5 and 240, and others. A receiver shows the type as 🏥 Vet practice to a user who reads English and as 🏥 Tierarztpraxis to one who reads de-AT. The phone number is stored as +49301234567; a receiver should show it grouped, such as +49 30 1234567, but never stores the form it shows. A receiver that checks may reject a record whose number holds spaces, naming the field phone (metadata, section 6.3).

Note

A label is the sender's word. A receiver that acts on a field because of its label, rather than because it knows the type, acts on what the sender says (metadata, section 8).
