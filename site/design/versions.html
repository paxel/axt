A type changes over the life of an app. Some changes let every app go on reading every record, old and new; all others make a new type. Knowing which is which decides how you change a type.

How receivers read another version

A receiver decodes a record with the writer schema it got with the offer or in the file header, and resolves it against its own schema of the type, by the schema resolution of Avro 1.12 (envelope, section 6):

  • The full names of the two record schemas match, or the writer's name is one of the reader's aliases.
  • Fields are matched by name. A writer field the reader does not have is ignored. A reader field the writer does not have takes the reader's default; without a default, the schemas do not resolve.
  • An enum symbol the reader does not know takes the default of the reader's enum; without one, the schemas do not resolve.

If the schemas do not resolve, the receiver declines the type with DOES_NOT_RESOLVE, or leaves the type's records in a file unapplied.

Versions and major versions

An example type carries its major version in its namespace: v1 in axt.example.v1.Note. Within a major version, the description of each version holds its version, an integer that is 1 for the first and grows by one with each version; the derived schema carries it as axt.version (types, sections 3.1 and 3.2; fields, section 9.1).

  • Compatible versions keep the full name, so a receiver with one version reads records of every other version of the same major version, in both directions.
  • A change that is not compatible publishes the type under the next major version, such as axt.example.v2.Note. The full names differ, so resolution fails at the name before any field is read, and a receiver can know both and read each with its own schema.
  • The major version belongs to each type, not to the set: Task stays axt.example.v1.Task while Note moves to v2.

These rules are binding for the example types. The description of a type of your own has a version as well, and it should count its versions in the same way (section 3.2), so that receivers can tell them apart (manifest, section 3.4). Resolution works by full name for every type, so the reasons behind the rules hold for yours as well.

Changes that keep a type compatible

A new version within the same major version makes only these changes against the version before it, in the type or in one of its nested records (types, section 3.3):

  1. add a field that has a default, under a name that no earlier version of the major version used;
  2. remove a field that had a default in every earlier version; its name is not used again within the major version;
  3. add a symbol to an enum, which has a default symbol;
  4. change doc texts, or add, change or remove the title or a hint other than unit and anchor, such as a label, a translation or the order of the fields, without changing what any value means;
  5. remove a check, or widen it so that every value that kept it still does: a lower min_length or min, a higher max_length or max.

Each keeps resolution working both ways. A receiver with the new version fills the added fields of old records with their defaults; a receiver with the old version ignores the added fields, fills the removed ones with its defaults, and reads an unknown symbol as the enum's default. A removed name is never used again, because a receiver that still has the old field would read the new one under the old field's type and meaning.

Changes that make a new major version

Every other change, among them:

  • changing a field's type, logical type or default;
  • changing unit or anchor;
  • renaming a field, adding a branch to a union, or removing an enum symbol;
  • keeping the encoding but changing what a value means;
  • adding a check or narrowing one, or changing a semantic brick or a pattern other than by removing it: a semantic brick replaced by axt.StringField, or no pattern. A sender never sends a value that breaks a check, so it could not send all its older records under the new version.

A record keeps the full name of its type for its whole life: every version of it is sent with a writer schema of the same full name, and a receiver rejects a record that comes back under another one with TYPE_CHANGED (records, section 4.3). A type in the next major version is a new type for new records.

One version, one fingerprint

In a live connection, a record names its schema by a fingerprint over the schema's Parsing Canonical Form, which drops doc, defaults, logical types and every attribute. The texts, hints and checks stay in the description and are not in the derived schema at all (types, section 3.4). Every published version of a full name must differ from the earlier ones in that form, so that the fingerprint tells them apart. A change of doc texts, texts, hints or checks alone is therefore not a version of its own: it waits for the next version that also adds or removes a field or a symbol.

Versions in the manifest and in what you send

  • Taking. A receiver's manifest names the versions it takes. It sets min_version above 1 only when it needs a field that earlier versions lack, and should leave max_version open, since later compatible versions still resolve (manifest, section 3.3; Write the manifest).
  • Sending. A sender that has several schemas of one full name may write a record with an older one for a receiver that takes only older versions. The fields that version does not have are then not sent (manifest, section 5.3; records, section 3).
  • An owner's devices on different versions. When one device of an owner sets a field that only a later version has, a device with an older version does not send that record to other apps, since the record it would send drops the value. It leaves the record to a device whose schema has the field (sync, section 5.1).

Note

Not every Avro library reads an unknown enum symbol as the enum's default, as Avro 1.12 requires. The Python avro package 1.12.2 raises an error instead, so a receiver built on it does not get the compatibility of added symbols (types, section 7.3).
