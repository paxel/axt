Every record an app exchanges has a type, named by its full name. A type is written as its description, from which its Avro schema is derived (Describe the fields). The first decision is whether a record of your app is one of the example types or a type of your own.

The example types

The repository brings example types under the namespace axt.example.v1, so that apps can exchange records without agreeing on a format first (types, section 1). There are eight:

TypeWhat one record is
NoteA text with a title, in plain text or CommonMark, with tags
TaskSomething to do, with a due time, a repetition, a priority and whether it is done
AppointmentAn event with a start, an end, a place and reminders
PersonA contact: names, birthday, phone numbers, email addresses and postal addresses
CarA vehicle: make, model, year, plate, VIN and odometer
PetAn animal the user keeps, such as a cat or a dog
MeasurementOne value at a point in time, with a UCUM unit, such as a pet's weight
DocumentA file with a title and a date, such as a scanned vet invoice

The table of types, section 7.1, lists their fields, and Example types shows each description and its derived schema. If a record of your app is one of these things, the example type is the one that other apps already know: Old Brain Fix can take cat-a-log's vet appointment because both use axt.example.v1.Appointment.

A type of your own

An app may use a type of its own for the same thing as an example type, or for a thing no example type covers (types, section 4):

  • It lives under a namespace of the app. The namespace axt and every namespace beginning with axt. are reserved for the AXT repository (section 2).
  • The namespace should be a domain that you control, in reverse order, such as org.example.catalog, so that two apps do not pick the same full name by accident.
  • You may start from a copy of an example type. The copy is then a type of your app, with its own full name and its own version from 1 on, and no longer the example type.
  • A type that only your app uses stays under your namespace; it is not added to the repository.

The full name is the type

A receiver knows a type by its full name alone. org.example.catalog.Pet is not axt.example.v1.Pet, even with the same fields. A receiver that wants to take your type as one it knows maps it on purpose: with your full name among the aliases of its own schema, or with code that converts the records. Without a mapping it declines your type, or shows the records from their schema if it takes any type (types, section 4).

So the cost of a type of your own is that other apps have to know it, or map it, before they can do more with it than show it.

Shaping a type

Every example type keeps the rules of types, section 5, and a type of your own should keep them too, so that receivers can show and map it. The derivation already gives the forms of optional values and defaults (fields, section 9.2). In short:

  • Documentation. The record, every nested type and every field carry a doc in English. A field's doc says what its value is and what an empty string, an empty array or null means in it (5.1).
  • Names. Records, enums and fixed types in UpperCamelCase, fields in snake_case, enum symbols in UPPER_SNAKE_CASE. A nested type is defined in place, and its name begins with the name of its type, such as PersonPhone in Person (5.2).
  • Optional values. A value that may be absent is ["null", T], with null first and the default null. A text that may be empty is a string with the default ""; a list is an array with the default [] (5.3).
  • Defaults. Give every field a default unless a record has no meaning without it, as an Appointment has none without its start. A field without a default can never be removed within the major version. Every enum has a default symbol; where reading an unknown symbol as a known one would change a value, as with a unit, that default is UNKNOWN (5.4).
  • Times. Dates, times of day, dates and times, and lengths of time are the time types axt.Date, axt.Time, axt.DateTime and axt.Duration, not Avro's logical types (5.5; time, section 3.2). The zone belongs into the axt.DateTime, not into a field of its own (5.6).
  • No id or version fields. The envelope carries the id and the version of every record (5.8).
  • Depth. A description is a tree of typed fields, so no type is recursive. No record nests deeper in records, arrays and maps than types.data_depth, which keeps a small message from exhausting a decoder's stack (5.7).
  • Labels and checks. Labels, help texts, emoji, formats and limits are in the type's description: Describe the fields.

A copy of an example type keeps these rules already, which makes it a good start for a type of your own.

One record that names another

A record can refer to another record of the same sender, such as a Measurement to the Pet it was taken of (records, section 8):

  • The reference is a field of the type string with the logical type uuid, or ["null", that] where it may be absent. It holds the id of the other record.
  • Its doc should name the type or types it refers to. No attribute marks a reference, so a receiver that does not know your type cannot tell it from another uuid field.
  • It names a record of your own app only, never one your app received from another app. A link to a record of another app is a relation (records, section 10).
  • The receiver may not have the other record yet, or may have declined its type. It keeps the reference and resolves it when the record arrives; it never rejects a record for it.

The example types of version 1 carry no references; Measurement names what was measured as text in subject.
