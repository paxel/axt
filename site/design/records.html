A record is sent once and then lives on: its sender updates it, deletes it, may bring it back. A receiver that lets its user change received records decides what happens when the sender's next message meets those changes.

Id and version

Every record carries an id and a version in the envelope, not in its fields (records, sections 2 and 3):

  • The id is a random or time-ordered UUID that the sender gives the record when it creates it. The record keeps it for its whole life, through every update, a deletion and a return after it. It is unique among all records of the sender, of all types, is never used for a second record, and is the same toward every receiver.
  • The version is a number that rises with every change of the record at its sender, a deletion included. It may have gaps: a sender that changes a record several times before it can send sends only the last state.
  • A receiver knows a record by its sender and its id together. Two senders' records with the same id are two records.

What a sender sends

  • An update is the whole record. A DATA message carries every field, the first version and every update alike. Toward another app no message carries only the changed fields (section 4.1).
  • A deletion is a version. A DELETE carries the id and the version of the deletion. A DATA with a higher version brings the record back under the same id, so a sender can undo a deletion (section 4.2).
  • The type stays. Every version of a record is sent with a schema of the same full name (section 4.3; Evolve a type).

How a receiver applies them

A receiver compares the version of each message with the highest version it has seen of the record (section 5.2):

Version in the messageThe receiver
No record under this idtakes the record, or keeps a tombstone for a DELETE
Higherapplies it, keeping its user's changes as below
Equalchanges nothing: a duplicate
Lowerchanges nothing: the message is older than what it holds

Messages can come twice, late or out of order, through a relay or from an old file. The rule makes the result independent of that: as long as the receiver's user changes nothing, the receiver ends in the state of the message with the highest version. A deleted record leaves a tombstone, its id and the version of the deletion, which the receiver keeps as long as it keeps the sender, so that an old message does not bring the record back (section 5.3).

The receiver's own changes

A receiver may let its user change received records. Those changes stay in the receiver: they are never versions of the record and are not sent back (section 1). If the user wants the sender to change the record, the receiver can propose it, where the sender takes proposals (Proposals). A record of its own that a receiver makes from a received one, even a copy, is a new record with an id of its own.

When an update arrives, the receiver keeps its user's changes, as far as it can per field (section 6). That leaves a few choices to the app:

Per field or the whole record

  • Per field, which a receiver should do: for each top-level field, it takes the sender's value if its user has not changed the field and keeps its user's value if the user has. A nested record, an array or a map counts as one value (section 6.1).
  • Whole record: a receiver that does not track fields treats any change as a change of the whole record, and either takes the whole update or keeps the record as its user left it (section 6.2).

A field counts as changed from the user's first change until the user discards it, for example with an action that takes the sender's value again. If an update brings exactly the user's value, the receiver may count the field as no longer changed. An app that lets its user propose changes merges per field for that type.

A deletion that meets changes

When the sender deletes a record that the receiver's user has changed, the receiver either deletes it or keeps it with its user's changes; it may ask its user (section 6.4). A record that the user has not changed is always deleted. A record kept against a deletion stays the sender's record under the same id, and a later update is merged into it.

While the user has not decided, the receiver reports that it kept the record, and reports again when the user takes the deletion after all (protocol, section 7.3).

A record the user deleted

A record that the receiver's user deleted stays deleted: an update does not bring it back unless the user agrees, and the receiver may offer to take it again (section 6.3).

What the sender learns

The receiver reports an outcome for each record message (section 7):

OutcomeMeaning
APPLIEDThe receiver took the record, or deleted it, as the message says
MERGEDIt took the record except the fields its user had changed, which it names
KEPTIt took nothing, because its user's change covers the whole record
DUPLICATEIt had this version already
STALEIt had a higher version already

The sender may show its user that a receiver kept changes of its own. A record withdrawn from a share has one more outcome, WITHDRAWN (Share records with other users). A file has no way back, so its reader reports nothing.

This receiver deletes in step 6 although its user had set the location, so the location is gone when the record comes back in step 7. A receiver that keeps changed records against a deletion reports KEPT in step 6 and MERGED in step 7, with the location.

On several devices

A receiver that runs on several devices of one owner is one receiver: its devices make every choice of this page alike, and a user's change or decision on one device reaches the others (section 6; sync, section 22.3; Run on several devices).
