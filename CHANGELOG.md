# Changelog

All notable changes to AXT are documented in this file.
Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning: [SemVer](https://semver.org/).

## [0.1.0]

### Added

- The repository skeleton: the directories for the specification, the example types, the test vectors, the conformance suite, the reference relay and the libraries, each with a README; an index of the specification documents as drafts; the licences (CC0 1.0 for the specification, types and vectors; Apache-2.0 OR MIT for code) and the rules for proposing types, specification changes and libraries. ([axt-1000](https://github.com/paxel/axt/issues/1))
- The envelope and encoding: every message is an `axt.Envelope` (format version, kind, sender key, record id and version, body, signature), sent in a live connection in Avro single-object encoding with the schema once in the offer, and stored in a file as an Avro object container file (codec `null` or `deflate`) with the record schemas in its header; the CRC-64-AVRO fingerprints, Avro 1.12 schema resolution, the representation of strings, times and UUIDs, size limits, the media type `application/vnd.axt` and the extension `.axt`, and annotated example bytes. ([axt-1001](https://github.com/paxel/axt/issues/2))
- The example types Note, Task, Appointment, Person, Car, Pet, Measurement and Document as Avro schemas under the namespace `axt.example.v1`, usable without prior agreement; the rules for types: the major version in the namespace and `axt.version` within it, the changes a compatible version may make, replacing a type with an app's own under its own namespace, a `doc` on every field, snake_case field names, defaults, logical types, time zones and all-day times, no recursion and a data depth limit of 32, the display attributes `axt.title` and `axt.unit`, and the CRC-64-AVRO fingerprint of every type. ([axt-1002](https://github.com/paxel/axt/issues/3))
- Records: every record has a stable id (a version 4 or 7 UUID, unique per sender) and a version that rises with every change its sender sends; a `DATA` message carries the whole record and a `DELETE` the version of the deletion; a receiver applies a message only if its version is higher than the one it has, treats an equal version as a duplicate and a lower one as stale, keeps tombstones for as long as it keeps the sender, and brings a deleted record back for a higher version; a receiver that lets its user change received records merges updates per field and keeps its user's values; the outcomes `APPLIED`, `MERGED`, `KEPT`, `DUPLICATE` and `STALE` and what an acknowledgement reports for each record; references between records of the same sender; and a worked example. ([axt-1003](https://github.com/paxel/axt/issues/4))
- The manifest: on connecting, each app sends an `axt.Manifest` in a `MANIFEST` message with its name, an optional URL, the envelope formats it reads, the types it takes (full name, a range of `axt.version`, where a schema without one counts as version 1, and one sentence in English on what it does with them, with translations keyed by BCP 47 language tag), whether it takes any other type with a sentence of its own, optionally the types it sends, and a revision that rises with every change; the sender offers only types that fit and shows the receiver's sentence in its user's language, and the receiver still confirms each offer; what a changed manifest means for later offers, which records a file's reader takes and what a file needs to carry a manifest, limits on counts, lengths and a 1 MiB body, the schema's fingerprint, and annotated example bytes for cat-a-log and Old Brain Fix. ([axt-1004](https://github.com/paxel/axt/issues/5))
- Keys, signatures and encryption: every message is signed with the sending installation's Ed25519 key over a fixed prefix and the envelope's bytes as received, the same live, through a relay and in a file, and verified strictly (S below the group order, keys and R canonical and of the group's prime order, so that the equations with and without the cofactor agree); an offer signs the schemas it carries and a receiver decodes a record only with schemas of its own sender; a file signs its `axt.schemas` with the header entries `axt.sender` and `axt.signature`, holds the messages of one sender, and is read with the published envelope schema only; the first contact by QR code or by trust on first use with the app name and a short fingerprint of 25 digits, what a receiver keeps of a known sender and what forgetting one means; messages through a relay are signed, padded and then encrypted with HPKE (DHKEM X25519, HKDF-SHA256, ChaCha20-Poly1305) to a separate X25519 key, which the manifest's new field `encryption_key` carries; the `KEY_MOVE` message with the schema `axt.KeyMove`, signed with the old key and carrying the new keys and a proof by the new key, confirmed by the receiver's user, after which ids and versions continue unchanged and the old key is rejected, with repeats, chains and the joining of a sender met twice; restoring a key, and what happens when a key is lost; annotated examples with test keys, and how Ed25519 libraries differ at the edges of verification. ([axt-1006](https://github.com/paxel/axt/issues/7))
